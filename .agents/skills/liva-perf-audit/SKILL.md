# LIVA Performance Audit

## Workflow

1. **Voice-Turn Latency Profiling**:
   - Run the automated voice turn latency decomposition test:
     ```bash
     npm run test:voice-turn
     ```
   - Analyze latency across the four critical voice turn milestones:
     - Milestone 1: `vad_end` (VAD detects speech completion, audio buffer flush).
     - Milestone 2: `stt_done` (STT audio transcription completes).
     - Milestone 3: `first_token` (Time To First Token / TTFT generated by LLM router).
     - Milestone 4: `first_speaker_frame` (TTS synthesizer emits first audio chunk to output stream).
   - Evaluate against LIVA SLA Latency Budgets:
     - STT Latency (`vad_end` -> `stt_done`): **< 150ms** (Parakeet-vi / Nemotron).
     - LLM TTFT (`stt_done` -> `first_token`): **< 400ms** (Metal / CUDA / CPU llama.cpp).
     - TTS Audio Lead (`first_token` -> `first_speaker_frame`): **< 150ms** (VieNeu / Piper).
     - Total Voice Turn (user stops speaking to assistant speaks): **p50 < 650ms, p95 < 850ms**.

2. **Native Performance Harness Execution**:
   - **TTFT Benchmark**: measure Time To First Token under clean conditions:
     ```bash
     cargo run -p liva-native-core --bin ttft_bench --
     ```
   - **Wakeword Benchmark**: evaluate false accept/reject and inference speed:
     ```bash
     npm run wake:benchmark
     ```
   - **Screen Vision Benchmark**: measure screen capture and vision tokenization latency:
     ```bash
     cargo run -p liva-native-core --bin screen_vision_bench --
     ```

3. **Memory & VRAM Benchmarking**:
   - Measure process RSS and working set memory:
     - On Windows: check `sysinfo::process_memory_bytes()` reported in `get_system_status`.
     - On macOS: inspect process RSS via `ps -o pid,rss,vsz,comm -p $(pgrep liva-native-core)`.
   - Run Concurrency & Memory Stress Test:
     ```bash
     cargo run -p liva-native-core --bin router_stress --
     cargo run -p liva-native-core --bin voice_stress --
     ```
   - Monitor VRAM allocation and GPU throttle limits via governor status (`system_gpu_percent`, `gpu_vram_bytes`). Ensure memory zeroization in enclaves and zero memory leaks under repetitive voice turn cycles.

4. **SQLite WAL Performance & Compaction Audit**:
   - Monitor SQLite WAL growth under sustained transaction volume.
   - Verify that the 60-second idle checkpoint worker (`spawn_idle_checkpoint_worker`) actively trims `.sqlite-wal` to avoid read amplification.
   - Benchmark query execution latency on indexed tables (`facts`, `conversations`, `messages`):
     ```bash
     sqlite3 <path-to-db> ".timer on" "SELECT count(*) FROM facts;"
     ```

5. **Automated Regression Assessment**:
   - Execute the automated repository scorecard:
     ```bash
     node scripts/scorecard.mjs
     ```
   - Inspect domain scores for `chat-luong-ma` (max 15), `kiem-thu` (max 20), and `van-hanh` (max 10).
   - Compare performance scores against historical entries in `tech-debt-ledger.json`.
   - Flag a regression if:
     - Voice-turn p95 latency exceeds 850ms.
     - TTFT exceeds 500ms on GPU-accelerated runners.
     - Process RSS memory grows monotonically without plateauing across 100 consecutive router calls.
     - SQLite WAL file exceeds 50MB after checkpoint interval.

6. **Audit Report Generation**:
   - Structure performance findings into a concise report:
     - Executive latency table: p50, p85, p95 vs SLA budget.
     - Milestone waterfall breakdown: VAD -> STT -> LLM TTFT -> TTS.
     - Memory footprint: baseline RSS, peak RSS, VRAM consumption.
     - Regression verdict: PASS / DEGRADED / REGRESSION.

7. **Safety Guardrails**:
   - Run heavy benchmarks (`router_stress`, `voice_stress`) in release mode (`--release`) to avoid unoptimized debug build skew.
   - Do not run performance benchmarks while production user audio or active voice sessions are running.
   - Follow repository Git boundaries: stage only authorized documentation or test baseline updates; never commit raw benchmark log files.
