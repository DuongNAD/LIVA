# OmniVoice Voice Cloning POC Performance & Compliance Report

This report presents the empirical verification, benchmarking, and stress-testing results for the OmniVoice Voice Cloning POC implementation located in `teamwork_projects/omnivoice_poc/`.

---

## 1. Performance Benchmarks

To measure latency accurately without altering the source codebase, a timing-instrumented binary (`benchmark.rs`) was introduced into the Cargo workspace under `rust_cli/src/bin/benchmark.rs`. 

The execution was divided into four distinct phases:
1. **Subprocess Invocation**: Spawning `export_onnx.py` to extract the voice style from reference audio and save a voice profile.
2. **Initial Loading & Setup**: Loading the generated voice profile from disk, phonemizing and tokenizing the input text, and initializing the ONNX Runtime (ORT) Inference Session.
3. **ONNX Inference Execution**: Extracting the 256-dimensional style vector slice and running the ONNX model inference.
4. **Audio Conversion & File Output**: Converting the float array waveform to 16-bit PCM WAV and writing the file.

### Key Performance Observations
- **Subprocess Invocation Bottleneck**: स्पौनिंग (Spawning) the Python subprocess is by far the slowest phase, consuming **62% - 70%** of the total execution time (approx. 3.0s sequentially). This is caused by `export_onnx.py` copying a massive **300MB ONNX model file** (`model.onnx`) and **54 voice profiles** (~28MB) from the `node_modules` cache into the local directory on *every single invocation*.
- **ORT Session Re-initialization**: Re-creating the ONNX Runtime inference session on every request adds **700ms - 2100ms** of overhead. Under higher concurrency, initializing multiple sessions concurrently saturates the CPU, tripling the setup latency.
- **Audio Output Speed**: Float-to-PCM conversion and WAV file serialization take negligible time (typically < 1 ms).

## 3. Concurrency & Regression Analysis

### Concurrency Vulnerabilities (Critique)

1. **Shared Temp File Collision (Race Condition)**:
   The CLI executes the Python subprocess with a hardcoded voice profile name: `--voice-name temp_voice`, and subsequently loads it from `voices/temp_voice.bin`.
   - When **5 concurrent instances** were launched, they all attempted to write and read `temp_voice.bin` simultaneously.
   - This resulted in a **100% failure rate** under 5 concurrency, throwing `NotFound` errors (Error code 2) because one instance truncated/deleted the file while another was trying to open/read it.
   - Even when concurrent runs succeed (e.g., due to thread scheduling offsets at concurrency=2 or concurrency=8), **silent data corruption** occurs: one request can read a voice profile generated by a concurrent request, mixing up voice styles.

2. **Severe Disk I/O Saturation**:
   Spawning multiple concurrent Python scripts—each copying 328MB of models and voices—causes massive disk I/O load. Under 8 concurrent requests, the system is forced to write **2.62 GB** of duplicate data to disk simultaneously, causing wall-clock time to degrade from 4.8s to 13.2s.

3. **Incomplete Subprocess Validation**:
   `validate_voices` in `export_onnx.py` loops over existing files in the `voices/` directory, but never checks if the generated `temp_voice.bin` actually exists. If file creation fails silently or lags, the validator returns success (since the other 54 files are valid), but the Rust CLI subsequently crashes when reading the non-existent file.

### Memory & Thread Lock Regression
- **Memory Leaks**: Because the CLI runs as a short-lived process, memory allocated by `ort` (ONNX Runtime) is fully reclaimed by the OS upon exit. However, re-compiling/re-loading the 300MB ONNX model on every call wastes RAM. If integrated into a long-running process (e.g., a node gateway or native core), this pattern would cause memory pressure unless the `Session` object is structured as a thread-safe singleton.
- **Thread Locks**: No deadlocks or permanent locks were observed in the Rust CLI binary. ONNX Runtime handles multi-threaded inference efficiently when running.

## 4. Recommendations for Production Integration

To integrate this POC into the production-ready `liva-native-core` (Rust) engine, the following modifications are required:

1. **Avoid Subprocess Spawning**: Spawning python processes on every request is a severe anti-pattern. The voice extraction logic (`scipy.signal.stft` and style standardization) should be ported directly to Rust (e.g., using `rustfft` or `ndarray`), or the Python part should run as a persistent service communicating via gRPC/IPC.
2. **Session Caching (Singleton)**: Load the `model.onnx` model into memory **once** at startup. Cache the `Session` object and share it across threads using a thread-safe container (e.g., `Arc<Session>`).
3. **Avoid File System for IPC**: Eliminate writing temporary files (`temp_voice.bin`) to disk. Pass the extracted style vector directly in memory as a `Vec<f32>` between the style extractor and the synthesis engine.
4. **Build Target Fix**: Update the Cargo build script (`build.rs`) or packaging script to automatically copy `onnxruntime.dll` to the target target folder on Windows to prevent out-of-the-box runtime crashes.
